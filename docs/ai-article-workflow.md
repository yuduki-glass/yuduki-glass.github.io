# AI活用記事の探索・選定・生成を行う半自動フロー

この手順は、人が開始を依頼し、AIがWeb調査・執筆・ローカル検証を行い、人が公開を判断する運用です。APIによる無人生成プログラムではありません。定期実行、Actionsの追加、ステージング、commit、pushは含みません。このファイルはJekyllのソースであるsite/の外に置き、サイトには公開しません。

将来は1日約5回の探索を想定しますが、毎回の記事生成は必須ではありません。通常の公開上限は1日3記事、目標は最低1記事です。最低品質条件を満たす候補がなければ、目標より品質を優先します。公開は別手順の [ai-article-publish.md](ai-article-publish.md) を、明示的な公開許可がある場合だけ使用します。この文書の更新は定期実行や自動公開の許可ではありません。

## 実行時に受け取る条件

- 探索モード：`通常探索モード` または `最終探索モード`。省略時は通常探索モードとし、時刻だけから最終探索と推測しない。
- 対象日：実行時のAsia/Tokyo（日本時間）の暦日。日次集計もこのタイムゾーンに統一する。
- 公開許可：生成・検証のみか、検証成功後の公開まで明示的に許可されているか。省略時は生成・検証のみ。
- 上限例外：人間が対象日と許可本数を明示した場合だけ適用する。最終探索モードや最低1記事の目標は例外許可ではない。
- 同日の探索記録と公開履歴：利用できる記録の場所と前回の実行状態。

将来の起動側がモード・日次記録・公開許可の範囲を渡します。時刻や実行回数は起動側の設定とし、この手順では固定しません。1回の実行で新規生成する記事は最大1本です。

## 開始時の依頼例

> 通常探索モードでこの手順を実行してください。当日の公開本数と探索記録を確認し、現在の一次情報で少なくとも5候補を比較してください。価値の高い候補があれば1本生成し、ビルドと追加依存関係なしのHTML検証まで行ってください。候補がなければ「今回は公開なし」と報告してください。既存ファイルを変更せず、commit・push・Actions変更は行わないでください。

最終探索ではモード指定を `最終探索モード` に置き換え、同日の過去候補も比較対象にします。公開まで依頼する場合は、その範囲を別途明示します。従来の「記事を1本作成」という依頼でも、品質・本数・検証条件は省略しません。

## 1. 作業前の状態と重複候補を確認

- リポジトリルートでgit status --shortとgit diff --cached --name-onlyを確認する。他の作業の変更を戻したり取り込んだりしない。
- site/_posts/のタイトル、category、tags、excerptと、候補テーマに関係する本文を確認する。
- 製品名が一致するかだけでなく、読者の目的、具体的な手順、記事で得られる成果が重複しないかを比較する。
- 既存記事と目的・手順・成果が大きく重複する場合は、言い換えて新規作成せず、別の実用テーマを選ぶ。
- 同じサービスでも、目的・機能・操作・得られる結果が明確に異なる場合は候補に含める。サービス名だけで除外せず、既存記事との違いを説明する。

### 当日の公開本数と処理中の記事を確認する

- 記事生成前に、Front Matterの日付が当日の記事と、当日の公開履歴を両方確認する。ファイル名の日付とも照合し、ローカルの未追跡記事や下書きだけで公開済みと数えない。
- 公開履歴は記事パス・URL、commit hash、対応するActions実行、Pages deploy、HTTP 200とローカルHTMLの照合結果、初回公開確認日時を根拠とする。Gitのcommit日時やFront Matterの日付だけを公開日時としない。
- 日次本数は日本時間の当日に初めて公開された記事の一意なURL数とする。過去日付の記事を今日初めて公開した場合も含める。既存記事の再デプロイ、修正、再確認は追加の1本と数えない。手動公開も含め、AI記事以外も含むサイト全体の新規公開を数える。
- 同日付の記事と履歴を照合し、不一致はorigin/mainの対象差分、Actions・Pages・公開ページの読み取りで確認する。記録がないことを0本の証拠にしない。本数を確定できない場合は生成・公開を停止し「本数確認不能」と報告する。
- 3本公開済みなら、探索を深掘りせず新規生成・公開なしで正常終了する。上限例外が明示されていれば、その日だけ指定された上限を使い、根拠を報告する。
- commit済み・push済み・deploy待ち・公開照合待ちなど、前回の未完了処理があれば0本扱いで別記事を作らず、その状態を報告して停止する。既存の検証済み未公開記事も再生成せず、依頼範囲を確認する。
- 将来の起動側は、生成から公開結果の記録までを直列実行し、同時実行や同一実行の重複起動を防ぐ。生成前と公開直前に本数・処理中状態を再確認する。日付をまたいだ場合は対象日と出典・本数・公開日を再確認し、無断で日付を書き換えず停止する。

## 2. 一次情報で複数の候補を比較してテーマを選ぶ

### 候補を探す方針

探索と生成は別段階にする。本数などの事前条件を満たす実行では、まず少なくとも5候補を調査して比較し、記事化判定を終えるまで記事ファイルを作らない。同日の有効な調査結果は再利用できる。候補不足なら探索範囲を広げるが、同じ候補の言い換えで水増しせず、不足が解消しない場合は理由と実際の候補数を報告して公開なしとする。次の条件を重視する。

- 最近公開された、または最近大きく更新されたAI機能・ツール・連携方法を優先する。公式の公開日・更新日と変更内容を確認し、検索結果の取得日や軽微な文面修正だけで「新しい」と判断しない。
- AIを使うことで、従来の手作業や通常の機能に比べて何が明確に便利になるかを説明できる用途を選ぶ。作業の削減や得られる結果を具体化し、未測定の時間短縮率などは書かない。
- 一般ユーザーがまだ知らない可能性のある使い方を探す。ただし認知度を調査していない場合は、「ほとんどの人が知らない」などと断定しない。
- 読者が準備から実行、結果の確認までたどれる、具体的な操作手順にできるものを選ぶ。
- 無料または低コストで試せるものを優先する。必要なプラン、無料枠、利用回数、対応環境、地域・言語、招待や段階的提供の条件も確認する。
- 単なる一般的なデジタル機能の紹介で終わらせず、AIが担う処理と、AI活用として記事化する理由を明確にする。実用性だけでこの条件を満たしたことにしない。
- 単なるニュースの紹介ではなく、「使い方」「実践」「検証」として、入力・操作・得られる結果・確認方法まで記事化できるか確認する。

### 比較とテーマ決定

候補ごとに一次情報のURLと確認日を記録し、以下の観点を比較表などにまとめる。

| 比較項目 | 確認する内容 |
| --- | --- |
| 新規性 | 公開・大幅更新の時期、変更点、今回紹介する価値。日付が不明ならその旨を記す。 |
| 実用性 | 誰のどの作業に役立つか、AIを使わない方法と比べて何が便利になるか。 |
| 手順の具体性 | 必要な準備、操作、入力例、結果の確認まで説明できるか。 |
| 一次情報の充実度 | 公式情報で機能・操作・制限・費用をどこまで裏付けられるか。 |
| 既存記事との重複 | 比較対象の記事と、目的・機能・操作・結果の共通点および違い。 |
| 読者が試せるか | 費用、環境、アカウント、提供状況などの条件が現実的か。 |
| 試しやすさ | 無料枠・低コストで試せる範囲と、課金や上限の条件。 |
| 実践記事にできるか | 発表の要約にとどまらず、使い方と結果の確認方法を示せるか。 |

点数付けは必須にせず、比較結果から選定理由を文章で説明する。「なぜ今紹介するか」「AIを使う利点は何か」「読者は何を試して何を得られるか」を明らかにし、他候補を見送った主な理由や未確認事項も残す。新しさだけで、実用性・検証可能性・試しやすさの不足を補ったことにしない。適切な候補がなければ探索範囲を広げ、確認できない仕様を推測して記事化しない。

### 事実・仕様を確認するルール

- 現在閲覧できる公式ドキュメント、公式ブログ、公式リポジトリを優先する。
- 操作・仕様・料金・上限について、それぞれ裏付けるURLと確認日を控え、本文の該当箇所にリンクする。
- 古い発表と現行ヘルプが異なる場合は現行の記載を確認し、確認できない仕様は省く。
- 料金が必要な手順なら、通貨、課金単位、適用条件も確認する。無料枠で完結するなら、その条件と上限を示す。
- 実機操作をしていない場合は「公式手順に基づく説明」とし、体験談や実測値を作らない。

### 記事化判定：通常探索モードと最終探索モード

最低品質条件は次のすべてを満たすこととする。

- 一次情報で、記事の中心となる事実・操作・仕様・利用条件を十分に確認できる。
- 既存記事と目的・手順・成果が重大に重複しない。
- AI特有の実用性が明確で、想定読者が実際に試せる具体的な手順と結果の確認方法を書ける。
- 未確認情報の断定、架空体験談、誇張を含めず、重要な制限を省いて誤解を招く内容にならない。

| モード・状況 | 判定と次の処理 |
| --- | --- |
| 通常探索モード、上限未満 | 最低品質条件に加え、新規性や最近の大型更新、実用性、試しやすさから「今記事化する価値が十分に高い」と説明できる最良の候補がある場合だけ1本生成する。なければ「今回は公開なし」で正常終了する。 |
| 最終探索モード、当日0本 | 同日の過去候補と今回の新規候補を合わせて再比較し、最低品質条件を満たす中で最も記事価値の高いものを1件選び生成する。通常探索で優先度が足りず見送った候補も対象にするが、最低品質条件は緩めない。 |
| 最終探索モード、当日1〜2本 | 最低1記事は達成済みのため通常探索と同じ判定を行う。3本まで埋めることを目標にしない。 |
| いずれのモードでも上限到達 | 新規生成・公開なしで正常終了する。 |
| 最終探索モードで最低品質条件を満たす候補なし | 公開せず、品質上の見送り理由と最低1記事を達成できなかった旨を報告する。 |

数値スコアだけで決定しない。通常探索の価値不足、最低品質条件の不適合、技術的エラーは区別する。候補の見送りは正常終了だが、必要な調査・本数確認ができない状態やbuild・HTML検証の失敗は「検証不能／失敗による停止」と報告し、公開へ進まない。公開許可がない場合は、採用候補も生成・検証までにとどめ、公開本数には加算しない。

### 同日内の探索結果を再利用する設計

同日の実行報告に加え、[日次探索状態管理](ai-article-state.md) の `scripts/ai_article_state.py` で、`runtime/ai-article-state/YYYY-MM-DD.json` に調査・判断の履歴を保存する。Python標準ライブラリのみを使用し、日付は日本時間、状態ディレクトリはGit管理外とする。通常探索では記録を読み、最終探索では見送りを含む同日の全候補を比較する。状態がない・壊れている・古い場合も公開0本と推測せず、当日付の記事と実際の公開履歴を照合する。本数を確認できなければ生成・公開を停止する。

状態管理は記録の読み書きだけを担当し、記事生成・採用・公開本数の判定・公開許可を自動化しない。保存は短い排他ロックと一時ファイルからの置換で行い、探索から公開までの直列実行は将来の起動側で保証する。状態ファイルは記事commitに混ぜず、自動削除しない。テストデータは専用サブディレクトリへ隔離する。

記録する最小項目は以下とする。

- 対象日・タイムゾーン・実行ID・モード・開始／終了時刻・実行結果。
- 候補の識別子（サービス、機能、用途、主な公式URL）、公開／大型更新日、最終確認時刻、比較結果、採用／保留／見送り理由、未確認事項、再評価の条件。
- 採用済み記事パス・slugと検証状態、公開処理中かどうか、commit hash・Actions実行URL・deploy結果・公開URL・内容照合結果・初回公開確認日時。

同じ候補は記録を読み、変更がなければ既存の根拠を使って比較する。新しい公式発表、大型更新、料金・利用条件・提供範囲の変更、以前の未確認事項の解消があれば再評価する。採用候補の重要な一次情報は生成前に再確認する。重大な重複や裏付け不足による見送りは、その原因が解消しなければ最終探索でも採用しない。記録が古い・欠けている場合は推測で埋めず、再調査と履歴確認を行う。履歴を回復できなければ停止する。

## 3. 新規記事を1本作る

前段のモード別判定と本数確認を通過した場合だけ実行する。未採用候補から記事の下書きを大量生成しない。

UTF-8のsite/_posts/YYYY-MM-DD-slug.mdを新規作成する。同じファイル名や公開URLが存在する場合は上書きしない。日付は予定公開日と一致させ、8項目を使う。

```yaml
---
layout: "post"
title: "読者ができるようになることを示すタイトル"
date: "YYYY-MM-DD"
category: "AI活用"
tags: ["AI活用", "対象サービス", "用途"]
slug: "lowercase-ascii-slug"
excerpt: "記事の対象・用途・扱う範囲を短く説明する。"
image: ""
---
```

本文のH1はレイアウトに任せ、H2/H3、手順、必要なプロンプト例、制限、出典を使う。説明用の例と製品仕様を区別し、誇張や水増しを避ける。関連する既存記事へのリンクは実在するURLだけを使う。

## 4. ローカルビルド

site/でPowerShellから実行する。BUNDLE_FROZENでロックファイルの更新を禁止し、不要なディスクキャッシュを抑える。以前からBUNDLE_FROZENを設定していた場合は終了後に元の値へ戻す。

```powershell
$previousBundleFrozen = $env:BUNDLE_FROZEN
try {
    $env:BUNDLE_FROZEN = 'true'
    bundle exec jekyll build --disable-disk-cache
    if ($LASTEXITCODE -ne 0) { throw 'Jekyll build failed' }
} finally {
    $env:BUNDLE_FROZEN = $previousBundleFrozen
}
```

依存関係やビルドに問題が出たら、既存設定・Gemfile.lockの変更で回避せず、原因を報告する。site/_site/は生成先であり、ステージングしない。将来日付の記事が出力されない場合も、無断で--futureを付けて検証済み扱いにしない。

## 5. 生成HTMLとGitの状態を確認

HTML検証だけのために新しいgem・パッケージ・ライブラリを追加しない。nokogiriを前提にせず、PowerShell標準機能やRuby標準ライブラリ、文字列比較・正規表現・ファイル存在確認で以下を検証する。完全なDOM解析は必須ではない。追加依存関係が必要なら導入せず停止する。Gemfile、Gemfile.lock、Bundler環境、Jekyll設定、Actionsを変更して回避しない。この制約は公開手順で行う再検証と公開HTMLの照合にも適用する。

例えば、Front Matterのtitleと生成HTMLのtitle・H1を比較し、本文の見出しやhrefがHTMLにあるか確認する。コードはHTMLエンティティを復元して元のコード本文と照合する。内部リンクは対応する公開対象の出力ファイル、一覧はURLの掲載を確認する。正規表現で必要箇所を取り出せなければ一致扱いにせず停止する。

- site/_site/YYYY/MM/DD/slug/index.htmlが存在する。
- title要素とH1がFront Matterのtitleに一致し、日付・URLも正しい。
- H2/H3、箇条書き、コードブロック、リンク先が本文どおりに生成される。
- 内部リンクに対応する出力ファイルが存在し、外部出典の内容を閲覧できる。
- トップページ・archives・sitemapに新記事のURLが入る。
- YAMLの8項目、category、インライン配列tags、ASCIIのslug、空のimageを確認する。
- 現行レイアウトが表示しないcategory、tags、excerpt、imageを、表示済みと報告しない。
- git diff、git diff --cached、git status --shortで、既存ファイルやステージに意図しない変更がないことを確認する。

## 6. 人に渡す結果

対象日・モード・公開許可の範囲、当日の公開本数と根拠、上限例外の有無、候補の比較結果と主な見送り理由、記録を再利用した候補と再評価した候補、採用判断を報告する。上限到達などで探索を省略した場合は、その理由を明記する。

記事を生成した場合は、選んだテーマと記事化する理由、出典と確認日、新規ファイル、タイトル、予定URL、要約、重複候補との違い、build結果、HTML検証の方法と結果、警告、最終git statusを報告する。生成しなかった場合は「今回は公開なし」と理由を示す。最終探索で0本のままなら、品質条件・エラー・許可不足など未達の原因を区別する。候補の比較は作業報告に含め、記事本文を水増ししない。

## 7. 明示的な公開許可がある場合の引き継ぎ

一次情報・重複・Front Matter・Jekyll build・生成HTMLの確認がすべて成功し、日次上限と実行状態を公開直前に再確認できた場合だけ、指定記事を [公開手順書](ai-article-publish.md) に渡す。本数目標だけで公開許可を補わない。既に明示された公開許可は再度要求しない。

公開手順書の安全装置を維持する。対象記事だけをステージングし、git diff --cachedで対象と内容を確認してcommit・pushする。対応するGitHub ActionsとJekyll build、Pages deployの成功、公開URLのHTTP 200、タイトル・H1・記事本文全体とローカル検証済みHTMLとの一致を確認する。本文比較では改行形式の差だけを正規化する。すべて成功して初めて公開確認済みとして日次履歴に反映する。途中で停止したものは処理中／失敗として残し、次の実行で二重生成・二重公開しない。

検証失敗時は公開しない。認証・ブランチ保護・Actions・Pagesなどのエラーでも、設定変更、依存関係追加、force push、無断の再実行などで回避しない。記事以外の変更や状態記録を公開commitへ混ぜない。公開結果は公開手順書の最終報告に従う。
