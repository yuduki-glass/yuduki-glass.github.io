今朝は10月8日〜9日朝の更新を中心に、「今日から使える」「運用を変える価値がある」ものを優先した。派手なモデル発表より、仕事の手数や失敗を減らす情報を上に置いている。今回は6件。

## 1. ChatGPT/Codexを会社で広げるなら「AIに専門家の仕事を手順化させる」がかなり現実的

**情報の確度：** 確認済み

**難易度：** すぐ試せる

### 何が話題？

OpenAIが10月8日、OracleでのChatGPT Work/Codex活用事例を公開した。OracleではChatGPT利用者が13万人、Codex利用者が9.5万人超。採用部門では人材市場調査の所要時間を98%減らしたとしている。重要なのは数字そのものより、「専門家だけができた調査・判断手順を、AIを介して他の担当者でも再利用できる形にした」という運用。

### つまり何ができる？

AIへ単発の質問を投げるより、「この仕事では最初にAを確認し、BとCを比較し、最後にこの形式で出す」という専門家の作業手順を固定した方が、組織では効果が出やすい。

### こんな人に役立つ

同じ調査・確認・資料作成を何度も行う人。新人へ仕事を教える人。属人化した作業を減らしたい人。

### 具体的な使用例

たとえばRPGプログラムの調査なら、「入口パラメータ確認→F仕様確認→SQL/RPGネイティブI/O確認→サブルーチン追跡→更新対象整理→不明点一覧」という読み方を手順として保存する。次回からコードだけ渡して同じ観点で調べさせる。

### 試し方

1. 自分が週1回以上やる作業を1つ選ぶ
2. ChatGPTに「この作業で私が毎回確認していることを、再利用できる標準手順にして」と頼む
3. 出てきた手順を自分で修正
4. 次回はその手順＋新しい材料だけ渡す

### 料金・制限・罠

ChatGPT/Codexの利用条件は契約プランによる。企業データを扱う場合は社内ルールと契約条件の確認が必要。

### 検証するとどこまで本当？

Oracleの利用者数や98%削減はOpenAI公式事例で確認できる。一方、同じ削減率が他社でも出る保証はない。再現性が高いのは「専門家の手順をテンプレ化してAIに再利用させる」という設計部分。

**情報源：** OpenAI公式

> **結月硝子一言：** AIを「何でも答える人」にするより、「この仕事のやり方を覚えた人」にする方が強い。業務改善ではこっちの方が効く。

## 2. Codex CLI 0.161.0、Windows/AMD環境で起動時クラッシュ報告

**情報の確度：** 確認済み

**難易度：** 該当者は注意

### 何が話題？

GitHub上で、Codex CLI 0.161.0がWindowsの一部AMD環境で起動時にクラッシュする報告が出ている。0.160.0へ戻すと動くという報告もある。

### つまり何ができる？

「昨日まで動いていたCodexが急に起動しない」という場合、設定を全部疑う前にバージョン差分を確認できる。

### こんな人に役立つ

WindowsでCodex CLIを使っている人。特にAMD CPU/GPU環境。

### 具体的な使用例

`codex --version` で現在バージョンを確認し、0.161.0で突然落ちるなら、既知Issueを確認して切り分ける。

### 試し方

1. `codex --version`
2. 直前まで動いていたバージョンを確認
3. GitHub Issueで同症状を検索
4. 必要なら一時的に旧版へ戻す

### 料金・制限・罠

旧版へ戻す場合は、新版で追加された修正や機能も戻る。業務PCでは勝手にバージョン変更せず、社内運用に従う。

### 検証するとどこまで本当？

GitHub Issueとして実際に報告が存在する。ただし全Windows/AMD環境で発生するわけではない。

**情報源：** GitHub Issue

> **結月硝子一言：** ツールが急死したとき、まず自分の設定を疑いがちだけど、昨日アップデートしたなら犯人候補はだいたいそこにもいる。

## 3. Geminiに「仕事を丸ごと進めるエージェント」機能が拡大

**情報の確度：** 確認済み

**難易度：** 中

### 何が話題？

GoogleがGeminiのエージェント機能を拡大している。単なる質問応答ではなく、複数ステップの作業を計画し、必要な情報を集め、成果物まで作る方向が強まっている。

### つまり何ができる？

「調べて終わり」ではなく、「調査→整理→比較→資料化」のような一連の仕事をまとめて依頼しやすくなる。

### こんな人に役立つ

調査資料、比較表、企画書、会議準備など、複数工程をまたぐ仕事が多い人。

### 具体的な使用例

「この3製品について公式情報を確認し、料金・制限・導入難易度を比較して、社内説明用の表にまとめる」のような依頼。

### 試し方

1. ゴールを明示する
2. 途中工程もまとめて渡す
3. 最終成果物の形式を指定する
4. 重要箇所だけ人間が確認する

### 料金・制限・罠

利用できるエージェント機能は地域・プラン・アカウントによって異なる。外部サービス操作では権限確認が必要。

### 検証するとどこまで本当？

Google公式の機能拡張として確認できる。ただし全ユーザーへ同時提供されるとは限らない。

**情報源：** Google公式

> **結月硝子一言：** 「AIに聞く」から「AIに仕事を渡す」への移行が、いよいよ普通になってきた。

## 4. GPT-6のIntelligent UI、Free/Goにも展開開始

**情報の確度：** 確認済み

**難易度：** すぐ使える

### 何が話題？

OpenAIがGPT-6のIntelligent UIをFree/Goユーザーにも展開し始めている。回答内容に応じて、表・カード・操作UIなどを生成する仕組み。

### つまり何ができる？

文章だけでなく、内容に合った操作画面や視覚的な表示をAI側が選べる。たとえば比較なら表、候補選択ならカード、設定なら操作UIという形。

### こんな人に役立つ

長文回答より、見て操作した方が早い作業をする人。

### 具体的な使用例

旅行候補の比較、商品比較、スケジュール整理、データ確認など。

### 試し方

特別な設定が不要なケースでは、普通にChatGPTへ依頼する。対応している回答ではUIが自動生成される。

### 料金・制限・罠

段階展開なので、同じプランでもまだ表示されないユーザーがいる可能性がある。

### 検証するとどこまで本当？

OpenAI公式の展開情報として確認済み。

**情報源：** OpenAI公式

> **結月硝子一言：** AIチャットの「全部文章で返す」という長年の癖がようやく崩れ始めた。人間、設定画面まで作文で読みたいわけではない。

## 5. コーディングAIでは「長いプロンプト」よりSPEC.mdのような永続仕様が効く

**情報の確度：** 複数情報源で一致

**難易度：** すぐ試せる

### 何が話題？

コーディングエージェント利用者の間で、毎回長い指示を書くより、リポジトリ内に仕様・制約・確認手順を置いてAIに継続参照させる運用が定着している。`SPEC.md`、`AGENTS.md`、README、プロジェクトルールなど名称はさまざま。

### つまり何ができる？

「このフォルダは触らない」「変更後はこのテストを実行」「命名規則はこれ」といった条件を毎回説明しなくてよくなる。

### こんな人に役立つ

Codex、Claude Code、Gemini CLIなどを同じプロジェクトで繰り返し使う人。

### 具体的な使用例

Excel自動化ツールなら、`SPEC.md`に「Pythonが実処理主体」「Controlシートはログ」「VBAはログを再解釈しない」「リネームもPython側で完結」と書いておく。次回の改修で設計思想がひっくり返りにくくなる。

### 試し方

プロジェクト直下に仕様ファイルを作り、最低限これを書く。

- 目的
- 触ってよい場所
- 触ってはいけない場所
- 実行方法
- テスト方法
- 設計上の重要ルール

### 料金・制限・罠

仕様ファイルが古くなると、AIが古いルールを忠実に守るという別の事故が起きる。コード変更と一緒に仕様も更新する必要がある。

### 検証するとどこまで本当？

各種コーディングエージェントの公式ドキュメントやコミュニティ運用で広く確認できる。ファイル名自体に絶対的な標準はない。

**情報源：** 各公式ドキュメント、GitHub、開発者コミュニティ

> **結月硝子一言：** AIに記憶力を期待するより、カンニングペーパーを机に置いておく方が堅い。人間の新人教育とだいたい同じ。

## 6. AIエージェントのSkills/MCP、便利さと同時に「誰のコードを実行しているか」が重要に

**情報の確度：** 確認済み

**難易度：** 中〜高

### 何が話題？

MCPやSkillsなど、AIへ外部ツールを追加する仕組みが広がる一方、悪意あるツール・依存関係・指示を経由したリスクへの注意も強まっている。

### つまり何ができる？

AIへGitHub、Slack、DB、ブラウザなどを接続すると非常に便利になるが、その分「AIが何を読めるか」「何を実行できるか」の権限設計が重要になる。

### こんな人に役立つ

AIエージェントへ外部サービスや社内データを接続している人。

### 具体的な使用例

GitHub連携なら、読み取りだけ必要な作業に書き込み権限まで与えない。外部MCPを入れる前に提供元とコードを確認する。

### 試し方

1. 接続中のAIツール一覧を確認
2. 各ツールの権限を確認
3. 不要な書き込み権限を外す
4. 出所不明のツールを避ける

### 料金・制限・罠

便利だからと権限を広げすぎると、誤操作時の影響範囲も広がる。特に本番DB、メール送信、GitHub書き込みなどは注意。

### 検証するとどこまで本当？

MCPやAIエージェントのセキュリティ設計として、公式ドキュメントやセキュリティ研究で継続的に指摘されている。

**情報源：** 公式ドキュメント、セキュリティ研究

> **結月硝子一言：** AIエージェントは優秀な新人というより、「言われたら管理者権限で実行しかねない新人」に近い。権限は先に絞る。

## 今日の観測

今日の6件を並べると、AIの進化は「モデルが少し賢くなった」より、**仕事の手順・UI・外部ツール・組織運用へ入り込む方向**が目立つ。

特に重要なのは、AIへ全部任せることではなく、

- 手順を固定する
- 仕様を残す
- 権限を絞る
- 人間が確認する場所を決める

という地味な設計。AIが強くなるほど、この地味な部分の価値が上がっている。
