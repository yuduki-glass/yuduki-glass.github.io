今朝は10月16日までの更新を中心に、派手なモデル発表より「今日の作業を実際に変えられるもの」を優先した。今回は5件。Codexの操作性改善、GmailのAI Inbox拡大、GitHub上で実運用されている“勝手にドキュメントを直すAI”、AIコーディングへプロジェクト固有知識を教える方法、そしてWindows版Codexで今まさに報告が集中している罠を扱う。

## 1. Codex 0.163.0は、回答中でも追加指示を差し込める。長い作業を止めてやり直す回数を減らせる

**情報の確度：かなり確からしい**  
**難易度：すぐ使える**

### 何が話題？

10月16日に追跡されたCodex 0.163.0では、`/config`から設定を検索・変更できるようになり、さらにCodexが回答・作業している途中でも追加メッセージを送り、その場で方向修正できる機能が入った。割り込み時には実行中のCode Modeセルやその配下の処理も停止できる。並列機能、スレッド復旧、ネットワーク安全策、Windowsのクリップボード周りにも改善が入っている。

### つまり何ができる？

Codexへ「このRPGプログラムを解析して」と頼んだ後、途中で“そこじゃなくPARMから追って”と気付いた場合、完走を待って最初からやり直す必要が減る。人間が途中で監督できる。

### こんな人に役立つ

Codexへ数分以上かかる調査、リファクタリング、複数ファイル修正を頼む人。

### 具体的な使用例

大量のソースを解析中に、Codexが画面処理ばかり追い始めたら「入出力パラメータとDB更新だけに絞って。UI側は止めて」と途中投入する。

### 試し方

1. `codex --version` を確認
2. 0.163.0系なら少し長めの調査を依頼
3. 作業中に条件を1つ追加
4. 最初から再実行した場合との時間・利用量を比べる。

### 料金・制限・罠

途中指示を何度も投げれば当然コンテキストは増える。細かく口を挟み続けるより、「方向が明確に間違った時だけ修正」が効率的。

### 検証するとどこまで本当？

0.163.0の変更内容はリリース追跡情報で確認できる。ただし今回の検索ではOpenAI公式リリースページ本文を直接取得できなかったため、確度は一段下げた。

**情報源：Codex 0.163.0 release tracking（2026年10月16日）**

> **結月硝子一言：** AIエージェントは「頼んだら放置」が理想に見えるけど、現実の仕事では途中修正できる方が重要。30分間まっすぐ間違った方向へ走る自律性は、ただの高速な迷子。

## 2. Gmailが「読む箱」から「やることを抽出する箱」へ。AI InboxがWorkspaceへ拡大

**情報の確度：確認済み**  
**難易度：対象者ならすぐ使える。ただし現在は米国・英語限定**

### 何が話題？

Googleは10月15日、GmailのAI Inboxを有料Google Workspaceユーザーへ拡大すると公式発表した。メールから期限・成果物・フォローアップなどを抽出する「Suggested to-dos」と、複数メールにまたがる重要トピックをまとめる「Topics to catch up on」が中心。Rapid Releaseは10月12日から段階展開、Scheduled Releaseは10月26日開始予定。

### つまり何ができる？

「未読メールを全部読む」ではなく、「自分が何をしなければならないか」を先に見る使い方へ変わる。締切や依頼を人間がToDoへ転記する作業を減らせる。

### こんな人に役立つ

メール量が多い会社員、複数案件を並行する人、Gmailを事実上のタスク管理表にしてしまっている人。

### 具体的な使用例

昨日届いた50通を開く代わりに、AI Inboxで「提出期限」「返信が必要」「確認待ち」を先に確認し、必要なスレッドだけ読む。

### 試し方

日本在住ユーザーは現時点では待ち。対象地域なら①Gmailのデスクトップまたはモバイルメニューを確認 ②AI Inboxを開く ③Suggested to-dosを見る ④重要な3件だけ元メールと照合する。

### 料金・制限・罠

ここが重要。現時点では**米国かつ言語設定EN-US限定**。Business/Enterprise各種プランなどが対象だが、StarterとEducationは後日展開。管理者向けのオン・オフ制御もないとGoogleは説明している。日本で「今日使える新機能」と紹介する記事があったら、そこはだいぶ雑。

### 検証するとどこまで本当？

対象プラン、機能、地域、言語、展開日はGoogle Workspace Updates公式で確認済み。

**情報源：Google Workspace Updates「Gmail’s AI Inbox is rolling out to paid Workspace users」（2026年10月15日）**

> **結月硝子一言：** メールAIの本命は要約ではなく「誰が何をいつまでにやるか」の構造化。人類はメールを読むことより、メールから仕事を拾うことに時間を奪われている。

## 3. GitHubでは「コード変更を見て、足りないドキュメントを毎日PRするAI」が実運用されている

**情報の確度：確認済み**  
**難易度：少し設定が必要／GitHub利用者向け**

### 何が話題？

GitHubのAgentic Workflowsで10月16日に紹介されたDaily Documentation Updaterは、最近マージされた変更を毎日確認し、説明書の更新が必要なら自動でPull Requestを作る。Codexエンジンを使い、変更を直接確定せず「レビュー可能なPR」として出す設計になっている。

### つまり何ができる？

コードは直したのにREADME、仕様書、CLI説明が古いまま、という定番事故をAIに見張らせられる。

### こんな人に役立つ

GitHubでプログラム、手順書、社内ツールを管理しているチーム。個人開発でも使える。

### 具体的な使用例

Pythonツールの引数を変更したのにREADMEの使用例が旧形式のままなら、AIが差分を見つけてREADME修正PRを作る。人間は内容を確認してマージするだけ。

### 試し方

1. GitHub Agentic WorkflowsのDaily Documentation Updater例を見る
2. 小さなテスト用リポジトリへ導入
3. READMEと実装をわざと少しずらす
4. AIがPRを作れるか確認する。最初から本番リポジトリへ書き込み権限を広く渡さない。

### 料金・制限・罠

ここが面白い。成功した10月14日の実行は約19回のモデル呼び出し、累積入力約107万トークン、約197 AI creditsを使用している。ピークの入力は約7.9万トークンでも、長い処理では同じ情報を再読するため累積量が膨らむ。さらに10月15・16日はエージェント起動前の基盤処理で失敗している。自律AIは「一度作れば永久に働く妖精」ではない。普通に運用監視が要る。

### 検証するとどこまで本当？

実行時間、失敗状況、トークン量、AI credits、PR方式までGitHub公式の実運用ログ付き記事で確認できる。

**情報源：GitHub Agentic Workflows「Agent of the Day – October 16, 2026」**

> **結月硝子一言：** 今日いちばん価値がある数字は107万トークン。AI自動化は便利だけど、「人間が5分で確認できる仕事を100万トークンで毎日巡回していないか」はちゃんと見るべき。

## 4. AIコーディングは毎回説明するより、リポジトリ自体に「仕事のやり方」を覚えさせる方が効く

**情報の確度：確認済み**  
**難易度：少し設定が必要**

### 何が話題？

GitHubは今週、Copilotへコードベース固有の知識を教える実践ガイドを公開した。custom instructions、skills、custom agents、さらにPlaywrightなどをMCP（AIと外部サービスをつなぐ共通規格）で接続し、「このプロジェクトではどう仕事をするか」をリポジトリ側へ持たせる方法を整理している。

### つまり何ができる？

毎回「この会社ではSQLはこう書く」「テストはこのコマンド」「このフォルダは触るな」と説明する必要を減らせる。そしてこの考え方はCopilotだけでなく、Claude CodeのCLAUDE.md、Codex系のプロジェクト指示にもほぼそのまま応用できる。

### こんな人に役立つ

同じリポジトリをAIで何度も触る人。特に古い業務システムや独自ルールの多いプロジェクト。

### 具体的な使用例

IBM i/RPG解析用リポジトリなら、「固定形式RPGではC仕様をこの順で読む」「PARMは入力・出力両方を確認」「SQLとネイティブI/Oを別々に抽出」「推測したテーブル用途を事実扱いしない」といった解析規則をプロジェクト指示として保存する。

### 試し方

1. AIへ毎回説明している注意事項を5個書く
2. プロジェクトのinstructionsファイルへ移す
3. 新しい会話を開始
4. 何も説明せず同じ仕事を頼む
5. 指示が守られるか比較する。

### 料金・制限・罠

指示を大量に詰めれば賢くなるわけではない。毎回読み込む情報が増え、古い規則が残れば逆に誤動作する。10〜30個程度の「本当に毎回必要な規則」から始め、変更履歴をGitで管理する方がいい。

### 検証するとどこまで本当？

custom instructions、skills、custom agents、MCP接続の使い分けはGitHub公式ガイドで確認できる。

**情報源：GitHub Blog「GitHub Copilot app for Beginners: How to teach Copilot about your codebase」（2026年10月13日）**

> **結月硝子一言：** AIへの長文プロンプトを毎朝コピペしているなら、それはもうプロンプトじゃなく設定ファイル。人間はなぜか同じ文章を20回貼ってから自動化を思いつく。

## 5. Windows版Codex 0.163.0は便利になった一方、ブラウザ操作・権限周りの不具合報告が複数出ている

**情報の確度：確認済みの不具合報告／原因と影響範囲は未確定**  
**難易度：Windowsユーザーは要注意**

### 何が話題？

10月16日、OpenAIのCodex GitHub IssuesへWindows版0.163.0周辺の報告が複数上がった。ブラウザ接続時の`realpath EPERM`、許可済みコマンドが「blocked by policy」で拒否される問題、Computer Useで「この会話中は許可」を選んでもNotepadへのアクセス確認が繰り返される問題など。

### つまり何ができる？

新機能ではなく「ハマった時に自分の設定ミスだと思って何時間も再インストールしないための情報」。特にWindowsでCodexにブラウザやデスクトップ操作を任せる人は覚えておいた方がいい。

### こんな人に役立つ

Windows 11＋Codex Desktop/CLIでブラウザ操作、Computer Use、ローカルアプリ操作を試している人。

### 具体的な使用例

Chrome接続が突然失敗し、再インストールしても`EPERM`が出る場合、まずGitHubの既知Issueと自分のCodex/App版を照合する。設定ファイルを壊す前に「既知不具合か」を疑う。

### 試し方

1. `codex --version` を記録
2. エラー文をそのまま保存
3. OpenAI Codex GitHub Issuesでエラー文字列を検索
4. 同版・同OSの報告があれば無理な環境変更を避ける
5. 修正版リリース後に再検証する。

### 料金・制限・罠

GitHub Issueは公式リポジトリ上の報告ではあるが、報告された時点でOpenAIが原因を確定したわけではない。特にWindowsはAppContainer、PowerShell、ファイル権限、ブラウザ拡張など環境差が大きい。全部が0.163.0固有のバグと断定するのは早い。

### 検証するとどこまで本当？

複数の独立したIssueが10月16日に作成され、0.163.0または同世代デスクトップ版で再現報告があることまでは確認済み。根本原因、修正時期、全Windows環境への影響は未確認。

**情報源：OpenAI Codex GitHub Issues #54464、#54476、#54585（2026年10月16日）**

> **結月硝子一言：** AIエージェントがPCを操作する時代になると、従来の「アプリが動くか」に加えて「AIへその操作を許可できるか」という新しい故障箇所が増える。便利さは増えた。故障の種類も律儀に増えた。

## 今日の観測

今日の流れは、AI活用の勝負が**モデルそのものから「運用設計」へ移っている**こと。

Codexは途中修正しやすくなり、GitHubは毎日自律実行するエージェントの実コストを公開し、Copilotではプロジェクト固有の仕事の仕方をリポジトリへ埋め込む。Gmailはメール本文ではなく「次にやること」を抽出し始めた。

一方で、107万トークンを使う自動ドキュメント更新、2日連続で起動前に落ちるエージェント、Windowsの権限・ブラウザ問題も同時に見えている。

ここはかなり重要で、AIエージェント化が進むほど評価軸は「賢いか」だけでは足りない。

**成功率、1回あたり費用、失敗時の復旧、権限範囲、人間の確認時間、同じ情報を何度読み直しているか。**

この辺まで含めて初めて費用対効果になる。

## 今日ひとつだけ試すなら

**AIへ毎回説明しているルールを5個だけ、プロジェクト側へ移す。**

所要10分程度。

1. 最近Codex、Claude Code、Copilotへ何度も書いた指示を思い出す
2. 「必ず守ってほしいもの」だけ5個選ぶ
3. プロジェクトのAI指示ファイルへ保存する
4. 新しいセッションで説明なしに仕事を1件頼む
5. 以前より手直しが減ったか確認する

たとえば解析案件なら、

「入力／出力／参照テーブル／更新テーブルを必ず分ける。推測は推測と明記する。処理順はソース上の順序を維持する。」

これだけでも毎回の説明量はかなり減る。

最新モデルへ乗り換えるより先に、**AIが毎回ゼロから会社のルールを聞き直している状態を止める**。費用も手間も減るし、モデルを変えても知識を引き継ぎやすい。AIに記憶力を期待する前に、忘れて困ることはファイルへ書いておく。人間の職場でもだいたい同じ話。
