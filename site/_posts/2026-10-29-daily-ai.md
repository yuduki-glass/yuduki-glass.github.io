今朝は10月28日にGitHub Universe 2026で一気に出た実務系アップデートが主役。数が多いので、単なる新機能カタログではなく「今日から仕事のやり方が変わるもの」に絞った。

## 1. Copilotが「どのAIを使うか」まで自動で決める。モデル選びを人間がやらなくてよくなる

**情報の確度：確認済み**

### 何が話題？

GitHub Copilot Fusionが一般提供になった。これは特定のAIモデルではなく、依頼内容を見て複数モデルを自動で振り分ける仕組み。簡単な仕事は軽いモデル、難しければ強いモデルへ昇格、場合によっては別モデルがレビューする。

### つまり何ができる？

「普段は安いモデル、難問だけOpusや上位GPT」という節約運用を、人間が毎回モデル切替しなくても実行できる。

### こんな人に役立つ

GitHub Copilotを日常的に使う開発者。特にモデルを頻繁に切り替えている人。

### 具体的な使用例

小さな修正は軽量モデルが処理し、品質チェックで怪しければ強いモデルへ自動エスカレーションする。GitHubはSingle、Cascade、Critiqueの3方式を使い分けるとしている。

**難易度：すぐ使える。**

### 試し方

- ①Copilotを最新版へ更新
- ②モデル選択でCopilot Fusionを選ぶ
- ③Standard / High / Maxから作業に合わせて選ぶ
- ④同じ依頼を固定モデルでも実行し、品質・時間・使用量を比較する。

### 料金・制限・罠

各モデルの標準料金に基づいて課金される。期間限定で有料Copilot利用者はFusion利用時のモデル料金が30%割引。安くなることは保証ではなく、依頼によっては複数モデルが動く。

### 検証するとどこまで本当？

GitHub公式ではFusion MaxがArtificial Analysis Coding Agent IndexでClaude Code + Opus 5.5 Maxの2点以内、平均APIコストは約半分、トークン数も約半分、時間は約40%短かったとしている。ただしベンチマークなので、自分の仕事で同じ数字になるわけではない。

**情報源：GitHub Changelog「Route and orchestrate models with GitHub Copilot Fusion」（2026年10月28日）**

> 結月硝子一言：昨日まで話していた「安いモデルで済む仕事は安いモデルへ」が、とうとう製品機能になった。人間が毎回モデル料金表とにらめっこする運用は、そろそろ機械へ返していい。

## 2. CopilotからSlack・Figma・Notion・Sentryなど26サービスへ、MCP設定なしで接続

**情報の確度：確認済み**

### 何が話題？

GitHubが公式確認済みMCPサーバーを「Connector」として提供開始。Slack、Figma、Notion、Sentry、Linear、Cloudflare、Vercelなど26サービスを、サービス選択→ログインだけでCopilotへつなげられる。

### つまり何ができる？

これまでMCP（AIと外部サービスをつなぐ共通規格）は「サーバーを探す→設定を書く→認証する→各クライアントで再設定」という技術者臭の強い儀式だった。新方式では一度接続すればCopilot app、CLI、VS Code、クラウド、GitHub Mobileで共通利用できる。

### こんな人に役立つ

GitHub Copilotを使い、Slack・Figma・Sentry・Notion等にも仕事の情報が散っている人。

### 具体的な使用例

「Sentryのこのエラーを調べて、関連するGitHubコードを特定し、修正案を作って」のような横断作業がしやすくなる。

**難易度：少し設定。従来のMCPよりかなり簡単。**

### 試し方

- ①Copilot appならCustomizeを開く
- ②接続したいサービスを選ぶ
- ③Connectして認証
- ④「このサービスの○○を確認して」と小さな読み取り作業から試す。CLIなら /mcp → Connectors。

### 料金・制限・罠

public preview。全Copilotプランへ展開中。Business / Enterpriseでは管理者がpreview機能やMCP allowlistを許可する必要がある場合がある。Slack側などでも管理者許可が必要なケースあり。

### 検証するとどこまで本当？

GitHub公式で26サービス、一度の接続で複数Copilot環境から利用可能と確認済み。

**情報源：GitHub Changelog「Connect your tools to Copilot without all the setup」（2026年10月28日）**

> 結月硝子一言：MCPの最大の弱点だった「便利らしいが設定が面倒」が削られ始めた。MCPが一般利用へ降りてくるなら、このConnector化がたぶん正攻法。

## 3. GitHubのAI自動化が「個人の便利機能」から「チームの業務システム」へ

**情報の確度：確認済み**

### 何が話題？

Copilot AutomationsにShared automationが追加された。これまで自動化は作成者個人に属していたが、共有版はリポジトリに属し、チームで閲覧・編集できる。作成者が退職しても動き続ける。

### つまり何ができる？

属人的な「○○さんのAI自動化」ではなく、チーム標準の作業手順としてAIを置ける。

### こんな人に役立つ

GitHubで複数人開発しているチーム、情シス、社内ツール担当。

### 具体的な使用例

Issueが作られたらバグを再現、PRがレビュー可能になったら画面キャプチャを作成、監視システムで障害を検知したら原因調査を開始、といった処理をチーム資産として持てる。

**難易度：少し設定。**

### 試し方

- ①自分だけが繰り返しているGitHub作業を一つ選ぶ
- ②Copilot AutomationをSharedで作る
- ③最初は読み取り中心の処理にする
- ④結果をチームで確認してから書き込み権限を増やす。

### 料金・制限・罠

AIクレジットはリポジトリ所有者側へ請求される。組織リポジトリでは管理者がクラウドエージェント利用を許可する必要がある。Pro、Pro+、Max、Business、Enterpriseへ展開中。

### 検証するとどこまで本当？

GitHub公式で共有、自動化の所有主体、請求先、変更履歴、退職後も継続する仕様まで確認済み。

**情報源：GitHub Changelog「Build shared workflows for your team with Copilot Automations」（2026年10月28日）**

> 結月硝子一言：自動化を作った本人が辞めた瞬間に誰も分からなくなる、という会社の伝統芸に一応対策が入った。

## 4. AI自動化に「使いすぎ防止」の予算上限。API破産対策が標準機能になってきた

**情報の確度：確認済み**

### 何が話題？

Copilot Automationsで、1回・1日・1週間・1か月単位のAIクレジット上限を設定できるようになった。同時に外部APIからの起動、24種類のGitHubイベント、MCP経由の外部機能、自動化同士の連鎖も追加された。

### つまり何ができる？

AIエージェントを24時間動かしつつ、「暴走して今月のAI予算を全部食う」を機械的に止められる。

### こんな人に役立つ

定期実行やイベント駆動でAIを使う人。個人よりチーム運用で重要。

### 具体的な使用例

Sentryで障害発生→Copilotが調査→修正PR作成→別Automationがレビュー、という連鎖を作りつつ、月間クレジット上限を設定する。

**難易度：少し設定〜技術者向け。**

### 試し方

- ①小さなAutomationを作る
- ②Per runの上限を低めに設定
- ③数回実行して実消費を測る
- ④その実測値から日・月上限を決める。

### 料金・制限・罠

複数Automationを連鎖させるほどコスト構造が見えにくくなる。上限なしで「AIがAIを呼び、そいつがまたAIを呼ぶ」は請求書に自我を持たせる行為。

### 検証するとどこまで本当？

GitHub公式でper-run、daily、weekly、monthlyの上限設定、REST API起動、24イベント、20の新GitHub機能、MCP接続を確認済み。

**情報源：GitHub Changelog「New tools, triggers, and cost controls for Copilot Automations」（2026年10月28日）**

> 結月硝子一言：AIエージェント時代は「何ができるか」より「最大いくら損できるか」を先に決める方が健全。

## 5. AI自動化が自分の失敗からプロンプト改善案を作る。ただし勝手には変更しない

**情報の確度：確認済み**

### 何が話題？

Copilot Automationsが実行結果から改善案を作るself-improvement機能を追加した。Issue分類なら人間が後からラベルを変更したか、コードレビューなら指摘が採用されたか、性能改善PRならマージされたか、といった実際の結果を学習材料にする。

### つまり何ができる？

人間が毎週「このプロンプト微妙だな」と手作業で調整する代わりに、AIが実績を見て修正案を出す。

### こんな人に役立つ

同じAutomationを長期間使うチーム。

### 具体的な使用例

PRレビューAIを毎回走らせ、開発者が無視した指摘と採用した指摘を一週間集計。週次Automationが元のレビュー指示の改善案を作る。

**難易度：少し設定。**

### 試し方

- ①成果を客観評価しやすいAutomationを選ぶ
- ②self-improvementを設定
- ③一週間程度実績をためる
- ④提案された変更を人間がレビューしてから採用する。

### 料金・制限・罠

AIが自分自身を書き換える完全自律方式ではない。変更は人間の承認が必要。これは欠点ではなく、むしろ必要なブレーキ。

### 検証するとどこまで本当？

GitHub公式で、実際のGitHub上の反応を信号として使い、prompt・tools・triggersの改善を提案し、人間が承認または拒否する仕組みを確認済み。

**情報源：GitHub Changelog「Copilot Automations now learn from outcomes and self-improve」（2026年10月28日）**

> 結月硝子一言：自己改善AIという言葉だけ見るとSFだけど、実態は「業務実績を見て設定変更案を出す」。この地味な形の方が仕事ではずっと使える。

## 6. PRが壊れたらCopilotが待機して、競合やCI失敗を勝手に直す

**情報の確度：確認済み**

### 何が話題？

Agent MergeがGitHubのPull Request画面へ統合された。PRを監視し、Actions失敗やマージ競合が発生すると、クラウド開発環境でCopilotが修正を始める。

### つまり何ができる？

PRを作ったあと、人間が何度もGitHubを開いて「CI落ちた→直す→また待つ」「競合した→rebase」の往復を減らせる。

### こんな人に役立つ

GitHubで日常的にPRを出す開発者。

### 具体的な使用例

Watch and fixを有効化し、Actions失敗とmerge conflictを監視。問題が起きればCopilotが修正し、auto-mergeと組み合わせれば条件を満たした時点でマージまで進める。

**難易度：すぐ使える。**

### 試し方

- ①PRのmerge欄でWatch and fixを選ぶ
- ②Actions失敗だけ、または競合だけを対象にする
- ③最初の数回は自動マージせず修正差分を確認
- ④品質が安定してからauto-mergeを検討。

### 料金・制限・罠

有料Copilotプランが必要。組織ポリシーにも依存。AIがCIを通した＝修正が正しい、ではない。テストが足りなければ間違ったコードも元気に緑色になる。

### 検証するとどこまで本当？

GitHub公式でPR画面統合、Actions失敗・競合の自動修正、auto-mergeとの併用を確認済み。

**情報源：GitHub Changelog「Agent Merge watches and fixes pull requests in the cloud」（2026年10月28日）**

> 結月硝子一言：AIコーディングの価値はコードを書く速度より、この「待ち時間と往復を消す」方が大きくなってきた。

## 7. AIアプリ特有の危険をGitHubがPR時点で検出。プロンプトインジェクションもコードスキャン対象へ

**情報の確度：確認済み**

### 何が話題？

GitHub Code ScanningがAIアプリ・AIエージェント固有の脆弱性検出をpublic previewで開始。間接プロンプトインジェクション、機密情報漏洩、過剰な権限などを検出する。

### つまり何ができる？

AIエージェントがWebページやIssueコメントに埋め込まれた悪意ある命令を読み、そのまま外部機能を実行してしまうような危険な設計をPR段階で警告できる。

### こんな人に役立つ

MCP、AIエージェント、外部機能付きチャットボットを開発している人。

### 具体的な使用例

外部Webページを読むAIが社内DB更新機能も持っている場合、「信頼できない入力→AI→強い権限」という経路を検出候補として出す。

**難易度：技術者向け。**

### 試し方

GitHub Advanced Security利用組織なら、AI applications scanを検証用リポジトリで有効化し、既存PRでどの経路が警告されるか確認する。

### 料金・制限・罠

GitHub Advanced Securityライセンスが必要。github.comのみでpublic preview、GitHub Enterprise Serverでは現時点で利用不可。静的解析なので全脆弱性を見つける魔法ではない。

### 検証するとどこまで本当？

GitHub公式でXPIA、機密情報漏洩、excessive agencyの検出とPR自動スキャンを確認済み。

**情報源：GitHub Changelog「Code scanning for AI applications in public preview」（2026年10月28日）**

> 結月硝子一言：AIに外部操作を許す会社が増えれば、プロンプトインジェクションは「変な返答をする問題」から普通のセキュリティ事故になる。ここは地味だけど重要。

## 8. 自社のデザイン部品を使って、会話だけで動く試作品を作るOSS「Replica」

**情報の確度：確認済み**

### 何が話題？

GitHub Designが社内で作ったAIプロトタイピングツールReplicaをMITライセンスでオープンソース化した。一般的なAI UI生成と違い、自社の既存コンポーネント、デザイン規則、ドキュメントを材料にして試作品を作る。

### つまり何ができる？

企画担当が「検索条件をGUIで組める画面を追加したい」と自然言語で説明すると、自社製品っぽい見た目・部品でインタラクティブな試作品を作れる。

### こんな人に役立つ

社内Webシステム、SaaS、業務アプリを作っているチーム。デザイナー・PM・エンジニア間の仕様確認に向く。

### 具体的な使用例

新しい検索画面を文章だけで議論する代わりにReplicaで動く画面を作り、「これで合ってる？」を先に確認してから本実装する。

**難易度：技術者向け。ただし利用者側は自然言語中心。**

### 試し方

- ①ReplicaのGitHubリポジトリを取得
- ②ローカル環境でセットアップ
- ③自社デザインシステムの小さな一部だけ登録
- ④一画面の試作品を作る。共有用Replica Hubは必要になってからでいい。

### 料金・制限・罠

Replica自体はMITライセンス。AIモデル利用やホスティング費用は別。既存デザインシステムが整理されていない会社では、AI以前に材料がぐちゃぐちゃという悲しい現実にぶつかる。

### 検証するとどこまで本当？

GitHub公式発表でオープンソース化、MITライセンス、自社コンポーネント・パターン・文書を利用する設計を確認済み。

**情報源：GitHub Changelog「Introducing Replica, an open-source AI prototyping tool」（2026年10月28日）**

> 結月硝子一言：AIにUIをゼロから妄想させるより「会社で既に使っている部品だけで作れ」はかなり合理的。業務システム向けAI生成はこの方向が強い。

## 今日の観測

今日はGitHubだけで十分なくらい大きな日だった。共通しているのは「AIを使う人間が毎回細かく面倒を見る」部分を消し始めたこと。

モデル選択はFusionが自動化。外部サービス接続はConnectorが簡略化。定型作業はAutomationが常駐し、チーム共有でき、予算上限を持ち、実績から改善案まで出す。PRはAgent Mergeが待機して直す。

つまりAIコーディングの競争が「コードを何行書けるか」から、「人間が席を外している間に、どこまで安全に仕事を進められるか」へ移った。

同時にGitHubは、AIアプリ用Code Scanningや権限制御、予算上限も入れている。自律化だけ進めて安全装置を後回しにすると、便利なAIエージェントではなく24時間稼働の事故発生装置になるので、このセットは重要。

## 今日ひとつだけ試すなら

今日はGitHub Copilot Fusion。

- ①VS CodeやCopilot appを最新版へ更新する。
②モデル選択でCopilot Fusionを選ぶ。
③まずStandardを選ぶ。
④普段よくやる小さな実作業を一件頼む。たとえば「このファイルの処理を説明し、バグ候補だけ指摘して。まだ変更しない」。
⑤次に普段使っている固定モデルでも同じ依頼を実行し、時間・回答品質・使用量を比較する。

Fusionが狙っているのは、まさに「簡単な仕事に高価なモデルを使う無駄」を人間に意識させず減らすこと。昨日まで“モデルを仕事ごとに使い分けよう”と言っていたのに、翌日にはその使い分け自体が自動化された。AI業界、こちらが運用ノウハウを覚える速度より製品側が仕事を奪う速度の方が速い。
